# R6-003 — provider adapter and outbound HTTP capture

Status: checkpoint approved after independent artifact recomputation,
2026-09-09. See the [review closeout](reviews/2026-09-09/R6-003-REVIEW.md).
Canned responses only. This checkpoint selects the OpenAI Responses wire interface
and a direct Python standard-library HTTP adapter. Model selection, live
credentials, sampling, spending and an external endpoint remain unset.

## Decision and scope

The selected transport is an explicit `http.client` transmission, with no
provider SDK, automatic retry, redirect following or solver fallback. The
existing broker LLM adapter emits tactic scripts; this policy preserves the
Farkas witness proposal interface and its downstream acceptance predicate.
No new Python package is needed. The interpreter, filtered standard library,
extension modules and ELF dependencies have a separate runtime inventory.

The API shape follows the [official Responses create reference](https://developers.openai.com/api/reference/python/resources/responses/methods/create),
inspected on 2026-09-08: a POST to `/v1/responses`, message input, a model field,
non-streaming output, completion status, message/text/refusal output items,
and optional usage. The choice is a project implementation decision, not a
claim that a particular frontier model or account is available. The frozen
wire model identifier is `r6-canned-model-not-a-live-selection`.

The executable runs a real HTTP client and local canned server inside the
existing Bubblewrap network namespace. The server binds only its private
loopback interface. It captures the actual request entity body independently
of the client's serialization record, then returns a host-prepared response.
It does not interpret the arithmetic or calculate a witness or request digest.
This tests local serialization, HTTP transmission and response handling. It
cannot establish acceptance by the remote OpenAI API, correct TLS/credential
handling, remote receipt, model-input interpretation or model computation.
The current CLI exposes no external endpoint or credential input.

The retained HTTP entity body is the application payload, not a packet capture
or TLS transcript. The recorded method/path, selected response headers and
status travel separately. Authorization is deliberately omitted from the
records; the isolated fixture uses a fixed non-credential marker and records
only its presence at the server. This describes the inspected implementation
and records; the approved suite contains no credential-leakage regression.
That control is a required [pre-live checkpoint](LIVE-POLICY-REQUIREMENTS.md#r6-003-approved-pre-live-credential-control--2026-09-09).

## R6-002 follow-ups

### Reachable arithmetic semantics

The new prompt and schema admit only integer `le` and `eq` rows. Integer
strictness has already been tightened by the compiler, so the model must not
add another one. A compiled D1 hypothesis `x.val < 16777216` supplies the
non-vacuous control: its emitted row is `_pb_atom_0 - 16777215 <= 0`. Both
independent projection and the fresh native D1 preparation must reproduce it.
The native episode also checks the used `neg_goal` row against
`P - 16777216 + 1 - 2·Zmax <= 0`. Its witness includes `hnum` to cancel
the otherwise large constant slack: the weighted sum is exactly `4`, and
omitting the integer `+1` would leave `0`, which is not contradictory.
The episode consumes this certificate and validates the original local and
containing targets. The `hx` projection check does not claim that `hx` itself
has positive weight in that witness. This is a pipeline/instruction consistency
control; no model has been tested for understanding the instruction. An extra
internal tightening could make a model compute `8` with the same weights,
which still verify against the authentic rows at `4`. This control does not
diagnose that internal behavior; observable row changes face separate checks.

Injected `lt` rows and Real-typed IR mislabeled as LIA fail before request
construction, including tests that drive production preparation. These
controls mutate IR fields; they do not claim elaboration of a new Real task. Admitting a
genuine strict row remains gated on a separately supported fragment and
compatible end-to-end consumption control. The R6-002 broad prompt is frozen
and unchanged.

### Diagnosable envelope differences

`outbound_envelope_binding` remains the common failure category. Its ordered
mismatch list identifies request options, message layout/role, system content,
user prefix, or exact request suffix. Unparseable input has a decode diagnostic.
Each component carries presence, byte length and SHA-256 where applicable;
an absent component uses null, while a present empty string has zero bytes and
its real digest. Multiple discrepancies remain separate and ordered.

The artifact auditor reconstructs these results from the captured HTTP body
and frozen expected messages. It does not trust the reported component name.
Corruptions alter/remove the system message, change the prefix, and change
only the arithmetic suffix while keeping a correct echoed digest. Rehashed
and resealed mutations falsely relabel a suffix failure as a system failure,
and falsely describe a missing message as a present empty one.

Response association, envelope agreement, provider-output decoding and witness
format/binding have separate predicates. Mathematical verification remains in
`certificate-verdict.json`. If an earlier boundary rejects, later verification
is unobserved; it must not be reported as a negative arithmetic result.

### One shared proof checker

The new auditor calls the unchanged
[`envelope_proof_audit.audit`](envelope_proof_audit.py). It does not add a third
copy of the proof-check block. The policy binds that module and its frozen
R6-002/R6-001 dependencies. Positive retained-only audits assert that the
production auditor invokes it. Separate resealed mutations reach that helper
and are rejected for altered consumed certificate, proof export, expected type
and forbidden axiom. Historical auditors remain unchanged.

## Response handling and accounting

The adapter makes one explicit connection/request. Its observations distinguish
reservation, connection attempts, body sends started, body sends returned, and
complete server captures. A failed connection consumes the reservation but
records no body send or server receipt. HTTP errors, disconnects and timeouts
after receipt retain that receipt. No status triggers a hidden retry; redirects
are returned as HTTP failures. A second invocation is rejected before another
stage starts. These are local HTTP observations, not billing evidence.

A killed adapter retains any observations it wrote. Missing observations after
reservation are unknown, not zero. The focused kill control supplies a partial
send/receipt record and verifies that supervisor failure does not erase it.

The response parser walks output items rather than assuming the first item is
a message. D1's response has a preceding reasoning item and two text parts;
C8 has one text part. Refusal, incomplete status, unexpected tool output,
malformed provider JSON, malformed witness JSON and a wrong echoed digest have
distinct detector categories. Well-formed wrong witnesses proceed to the
independent certificate verifier and fail there.

D1 reports synthetic input/output/total usage plus cached/reasoning details;
C8 reports no usage. Unknown fields remain null, and known zero remains zero.
Malformed details, inconsistent totals and output above the requested limit
are rejected. These numbers are fixture data, not tokenizer measurements.
`live_model_calls = 0` and `live_model_cost_usd = 0` describe the actual local
experiment. The separately reported cost remains null.

Provider-reported model/response identifiers are recorded as such. Agreement
with the request identifies the declared response; it does not verify a model
revision or attest to inference. An echoed request hash remains association
only, including when the body was ignored or altered.

## Witness and proof scope

The host selects `8·hZ + 4·neg_goal + 4·hnum` for D1 and
`1048576·hhi + 4·neg_goal` for C8. C8 rescales a known witness. D1 adds the existing constant inequality
`hnum` to make the integer-tightening control decisive. Neither is learned
proposal generation or SDK synthesis. Attribution is
`witness_proposer = canned_provider_response`,
`certificate_assembler = sdk_proposal_assembler_v1`, route
`openai_responses_http_fixture_v1`, certificate `farkas`, tier 1.

The SDK verifies the assembled certificate and Lean consumes it through the
existing Farkas helper, followed by residual `omega`. ATP derivation replay is
false; independent replay of the resulting Lean proof is separately required.
The generic `search_succeeded` field means the canned candidate succeeded.
It does not indicate discovery by a search algorithm.

D1 validates an obligation inside VerInf's real containing declaration. C8's
containing theorem remains a statement-identical `exact hlt` wrapper, testing
local-proof binding rather than a larger downstream embedding. C8's large
coefficient exercises proposal consumption; it does not exercise deterministic
witness recovery. The two controls and repeated D1 serialization run provide
no additional benchmark breadth. P6's translation-loss stratum is unchanged.

execution. A development-only option places versioned locks under the ignored
R6 cache; development receipts are excluded from the publication checkpoint.

```bash
python3 experiments/r6/test_provider.py --run-dir experiments/r6/runs/provider-reproduction-v1

```

Suites start red and assert independent exact case-name sets with no duplicates
before writing green. Accepted episodes have their ordinary seal. Rejected
episodes retain `failure.json`, a terminal failure event, and a separately
named `failure-seal.json` with `accepted: false`; they have no accepted verdict
or completion event. The rejected-episode auditor checks the recorded failure
boundary without claiming a proof success.

The preservation snapshot comes from Git `13baa73`, including C1, frozen tasks,
runs, schemas, policies and earlier locked sources. It does not bless the
working tree as baseline. Retained-only audits replay the audit logic over
saved evidence; they do not run Lean again.
