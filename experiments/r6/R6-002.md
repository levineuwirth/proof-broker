# R6-002 — semantic prompt and envelope binding with canned responses

Status: checkpoint approved after independent artifact recomputation,
2026-09-08. See the [review closeout](reviews/2026-09-08/R6-002-REVIEW.md).
No live model calls. This is an interface checkpoint, not a capability result.

The new `canned_envelope_v1` policy puts the arithmetic semantics into an exact
UTF-8 prompt, binds that prompt into the task request, and captures the bytes
read by an isolated canned receiver after serialization. It checks three
different propositions separately: the response carries the expected request
identifier; the captured messages contain the frozen instructions and exact
arithmetic request; and the proposed witness verifies and can be consumed in a
proof of the frozen target.

The receiver deliberately does not parse or use the request body. A passing
digest echo therefore provides a concrete control for the limited meaning of
response/request association. The altered-message controls retain that passing
echo and fail envelope validation. The well-formed invalid witnesses retain
both successful transport checks and fail independent certificate verification.

## Prompt, request and transport

The prompt spells out the semantics in the pinned
[`farkas.ml`](../../sdk/lib/farkas.ml): row relations, already-tightened integer
bounds, `neg_goal`, signed equality multipliers, nonnegative inequality
multipliers, variable cancellation, and the constant/strictness contradiction
test. The request only admits these controls' independently projected LIA rows.
No arithmetic few-shot example is supplied; the displayed JSON uses explicit
shape placeholders. The text includes the general strict-row rule of the
verifier; these two controls exercise tightened non-strict rows, not coverage
of every arithmetic theory or prompt interpretation.

The byte construction is:

1. Hash the exact prompt bytes, including whitespace and the final newline.
2. Include that hash, the policy hash, and task/challenge/input/final-IR bindings
   in the canonical request JSON. Hash the request bytes including its newline.
3. Put the actual prompt text in the system message. The user message begins
   with the supplied request digest and then contains the exact request bytes
   as a UTF-8 suffix. The request does not contain its own digest.
4. Retain `client-arguments.json` and `messages.json`. Serialize the arguments
   into `serialized-envelope.json`. Retain the actual received bytes separately
   as `stages/proposal-1/output/received-envelope.json`, with a native byte-count
   receipt. Audit those bytes, not merely the serializer's input arguments.
5. Validate the response identifier, grammar and support independently of the
   captured-envelope check. Retain both outcomes in `transport-validation.json`.
   If both checks fail, envelope failure has fixed precedence; the other result
   remains recorded.

The standard serializer emits indented ASCII-escaped JSON. A positive control
uses compact UTF-8 JSON instead. Their bytes differ, while the decoded messages,
prompt bytes and canonical task request agree. The accepted audit checks the
declared case's serialization and separately reconstructs the expected messages.

This checkpoint uses a **provider-neutral local file transport**. There is no
provider SDK, HTTP client, remote receipt or model. The C receiver reads
`/wire.json`, saves the bytes, and copies `/canned.json` to stdout. It does not
parse JSON, calculate a hash, or consult the arithmetic. The harness prepares
the canned response, including its digest, before invoking it. The request is
an input to the byte-capture operation, not an input used to derive the witness.

The receiver has read-only mounts for its runtime libraries, serialized
envelope, canned response, and executable. It receives no pristine source,
human proof, sanitized Lean telescope, or separate IR file. The inherited
environment is cleared and the existing explicit `PATH`/Lean-panic settings
are applied. `/out` is the sole host-backed writable directory, alongside the
existing temporary/process/device mounts and namespace/resource isolation.
The audit checks the complete recorded command, including mount sources.

The actual provider adapter is still future work. Before its first live call,
canned responses must exercise that adapter's serialization and exact outbound
boundary as required by [LIVE-POLICY-REQUIREMENTS](LIVE-POLICY-REQUIREMENTS.md).
Passing this local checkpoint does not establish that any provider SDK preserves
these messages, or that a remote model receives or uses them.

## Witness and acceptance path

The positive D1 witness is `6·hZ + 3·neg_goal`; the positive C8 witness is
`786432·hhi + 3·neg_goal`. These deliberately use different rescalings from
R6-001's canned witnesses. They are host-selected controls, not synthesized or
learned proposals. The SDK assembles a certificate from the supplied vector;
the separate verifier checks it; Lean consumes it via
`ProofBroker.TermMode.farkasContradictN` and closes the residual with `omega`.

Attribution remains explicit: `witness_proposer = canned_response`,
`certificate_assembler = sdk_proposal_assembler_v1`, tier 1, certificate type
`farkas`, and route `canned_envelope_v1`. The unchanged mechanical certificate
backend name is `r6_fixture_witness`; it names the shared delivery interface,
not an independent search producer. No ATP derivation is replayed
(`derivation_replayed = false`). Independent replay of the resulting Lean proof
is a separate required operation (`proof_replayed = true`).

`search_succeeded` retains the episode's candidate-success predicate. Here the
candidate is canned; a true value does not report discovery by any search system.

Both local closure and containing-declaration validation remain mandatory.
D1 is embedded in the real VerInf `lift_cell` development. C8's container is
a statement-identical `exact hlt` wrapper: it checks binding to the saved local
proof, not embedding in a larger real context. These two containing-replay
checks must not be reported as equivalent populations. The new C8 witness
tests the proposal/assembly/consumption path for a large multiplier; it does
not exercise SDK witness recovery, whose branch controls remain R6-000/C1.

## Admission and accounting

An exact four-field projection keeps every genuine hypothesis, including D1's
six let-bound facts, and excludes values and the declaration placeholder.
This sanitized telescope remains evaluator reference material, not model-visible
context. A `_proof_` reference in an otherwise legitimate original type now
produces `context_admission_review_required`. A projection with an injected
body, placeholder or missing genuine fact produces `payload_integrity_failure`.
The paired controls reject before any request. These are synthetic context-field
classification tests; they do not claim Lean elaboration of the synthetic
context. A separate test calls production preparation with a review-required
source type and verifies that request construction and later preparation stages
have not occurred.

P6 remains in the unchanged translation-loss diagnostic stratum. Its frozen
membership criterion and independently checked IR counterexample are verified;
no proposer outcome affects membership. These two canned controls add no claim
about P6 recovery or the completeness of the reifier.

`accounting.json` distinguishes **attempts reserved** from **completed receiver
captures observed**. Reservation consumes the attempt budget before invoking
transport; a timeout or transport failure after capture still records one
transmission. The second-attempt control fails before launching another stage.
A missing capture cannot be inferred from process success. It is an explicit
transport-capture failure.

The canned receiver reports no token usage or price. Its input/output/total
token and reported cost fields are `null`, not zero. Unit controls distinguish
unreported usage from an explicitly reported zero or partial report. The
separate fields `live_model_calls = 0` and `live_model_cost_usd = 0` describe the
known actual experiment, which invokes no model; they are not estimates of
simulated/provider usage. No token-cost comparison is justified here.

New failures carry the raw `failure_stage`, the explicitly mapped
`failure_phase`, and a boundary category. Their causal attribution remains
unassigned. Historical failure records are not rewritten.

## Reproduction and review

Run from the repository with the frozen dependencies and a functioning user
systemd resource monitor/Bubblewrap environment. Each run directory must be new.

```bash
python3 experiments/r6/test_envelopes.py --run-dir experiments/r6/runs/envelope-reproduction-v1
python3 experiments/r6/envelope_episode.py audit --run-dir experiments/r6/runs/envelope-checkpoint-v1/d1_valid
python3 experiments/r6/envelope_episode.py audit --run-dir experiments/r6/runs/envelope-checkpoint-v1/c8_valid
```

The native suite executes the frozen two-task population through fresh capture,
certificate checks, reconstruction and independent kernel validation. Retained
artifact audits subsequently check those recorded results; they do not execute
the proof assistant again. Tests start red, write each completed case immediately,
and assert independent exact case-name sets, including uniqueness, before
writing green. Negative controls retain failure markers and no completion seal.
Audit mutations rebuild the event chain and seal and assert that a mutation
actually changed bytes before checking its rejection.

The preservation guard derives the prior-artifact hashes from Git `79a4a07`,
including C1, frozen tasks and runs through R6-001, policies, schemas and locked
downstream harness files. It does not take the current working tree as baseline.
Documentation amended by this checkpoint is outside that preserved artifact set.
