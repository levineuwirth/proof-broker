## The relationships, as decided

**Contract.** Exact instruction bytes (`prompts/farkas-lia-v1.txt`, 2,143
bytes, `30fcc51b…` — the same instruction digest both live D1 runs carried),
the rendering rule (roles, prefix, separator, request and entity-body
encodings), the request schema (`r6-farkas-request-9`, row relations and
semantics, context policy), the response schema, the model identity, the
generation options exactly as sent plus fourteen options that must stay
omitted, and the seven scientific resource limits. Frozen as canonical bytes;
`cohort_contract.contract()` refuses a file that differs from its inputs.

**Request.** `contract_sha256` plus the existing task, manifest, challenge,
input-IR, final-IR and prompt bindings; no policy digest. Schema
[cohort-request](schema/cohort-request.schema.json).

**Policy.** `contract_sha256`, the campaign identity and schedule, the
authorization, the pricing evidence and the spending limits.
`pricing_gate_v3.check_policy` rejects a policy whose generation options,
scientific limits or model differ from the contract's.

**Host and actor.** `pricing_gate_v3.admission` recomputes the whole envelope
from the request under the contract — instruction bytes, both messages, every
generation option, absence of every omitted option, sizes — and compares it to
the arguments the sender is about to serialize; then the v2 pricing rules.
The host runs it before reserving; the actor runs it again inside the sandbox
against the mounted contract and instruction file and binds the result to the
host's permit. Controls cross the envelope six ways at the host and three at
the actor (altered instruction text, an omitted option present, a changed
generation option, a foreign contract digest, changed instruction bytes); each
is rejected with its own code and zero connections.

**Campaign identity.** `cohort_ledger` keys the ledger by a campaign id
chosen at the first freeze; each policy revision is *registered* in the
ledger (same identity, same contract, same purpose, schedule not shrunk, money
not below committed, no open reservation, not already registered) and only
the latest registered revision can reserve. Reservations name a (task, draw)
slot; a consumed slot stays consumed across revisions; a released slot may be
retried up to the pre-send limit; an `unknown` outcome consumes the draw. The
slot identity lives in host and actor receipts and in the ledger, never in
the model-visible bytes. Distinct campaigns sharing the contract are distinct
directories.

## The demonstration

Two pricing captures (`pricing-approved-campaign-1` at 08:10 UTC and
`pricing-approved-campaign-2` at 11:57 UTC; extracts byte-identical, raw
pages different) gave two policy revisions of one campaign. Five episodes:

| Run | Revision | Slot | Outcome | Ledger |
| --- | --- | --- | --- | --- |
| r1-d1-draw1 | 1 (`685fda57…`) | D1 / 1 | proof accepted, `cd6081da…`, 3,702 / 3,721 | `send_grant` |
| r1-d1-draw2-format | 1 | D1 / 2 | `credential_format` (forced), 0 connections | `release`, attempt 1 of 3 |
| r2-d1-draw1-refused | 2 (`da3d268d…`) | D1 / 1 | refused at reservation: `cohort_slot_consumed`; sealed `episode_rejected` | none |
| r2-d1-draw2 | 2 | D1 / 2 | proof accepted | `send_grant`, attempt 2 |
| r2-d1-draw3 | 2 | D1 / 3 | proof accepted | `send_grant` |

- **Identical model input.** The entity body handed to the sender is
  `e684c116…` in all four runs that reached transport — across both
  revisions, both captures and both policy digests.
- **Distinct execution receipts.** Four distinct reservation ids, three
  distinct grant ids, four distinct commitment nonces; each receipt carries
  its slot (`verinf-d1-70/N`) and revision.
- **Continuous accounting.** One ledger: `activation, reservation,
  reservation, release, authorization_revision, reservation, send_grant,
  reservation, send_grant`; slots 1, 2, 3 consumed; slot 2 shows one release
  and two reservations; 307,200 µUSD committed; the revision-1 digest can no
  longer reserve (`cohort_revision_not_current`, controlled).

Cache usage is recorded per run beside order, latency and cost
(`usage.cached_tokens`; the canned fixture reports 2). The design recommends
eight blocks with one draw of each task per block; interleaving balances order
without establishing independence or removing cache effects.
