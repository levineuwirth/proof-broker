# R6-001 — fixture proposals through the Farkas boundary

Status: checkpoint approved after independent artifact recomputation,
2026-09-08. No model calls. See the [review closeout](reviews/2026-09-08/R6-001-REVIEW.md).

This step establishes an interface for an untrusted witness proposer. A native
fixture returns a request-bound coefficient vector; the SDK assembles a Farkas
certificate, a separate verifier checks it, the Lean bridge consumes it, and
independent replay checks the frozen local and containing declarations. The
fixture is a transport and boundary control, not a proof-search experiment.

## Scope and context decision

The implemented request policy is `farkas_rows_only_v1`: compiled arithmetic
rows from the final IR, plus task, challenge, input-IR, final-IR and policy hashes.
The policy hash binds the frozen admission record. This is a strict arithmetic
IR interface. The fixture reads exactly `request.json` and its selected witness;
its executable and required runtime libraries are the other read-only mounts.
There are five read-only mounts: libc, the dynamic loader, `request.json`, the
selected fixture witness, and the fixture executable. The inherited environment
is cleared, then `PATH=/no-programs` and `LEAN_ABORT_ON_PANIC=1` are set. Network
and process namespaces are isolated; `/out` is the single host-backed writable
output directory. The sandbox also supplies temporary/process/device mounts.
The R6 resource monitor bounds the workload.

Each row means `constant + Σ coefficient × variable ≤ 0`, `< 0`, or `= 0`, as
indicated by `relation`. For these LIA controls the compiler turns strict integer
bounds into non-strict bounds by adding one. `neg_goal` is the negated target.
Witness entries refer to row names. Responses contain decimal integer
coefficients and the SHA-256 of the **exact request bytes**, including the final
newline. The SDK verifier decides mathematical validity; the response decoder
only checks grammar, size, unique/known references, and request binding.

The fixture does not compute that digest. `RequestSession.invoke` hashes the
request and supplies the digest as a command-line argument. The fixture opens
`/request.json`, counts bytes, returns 4 if none were read, and echoes `argv[2]`.
Its file guard checks only that the file opens and yields at least one byte;
it never parses the request JSON or uses the arithmetic rows. The response
validator independently recomputes the expected digest. A matching echo checks
the response's association with the recorded request. It is not evidence by
itself that the proposer read or used the request, and it is not an inference
attestation. The fixture's read loop is established by inspection of its frozen
source, subject to the existing host/build/execution trust assumptions. In the
`wrong_binding` control the harness supplies `'0'*64` as the digest argument.

The original Lean telescope is evaluator reference material. A separate
`sanitized-context.json` keeps precisely `name`, `type`, `binder_info`, and
`index` for every genuine entry, including lets, and drops the declaration
placeholder. No `value` field or `_proof_` string is permitted. This projection
is **not sent to the fixture/model interface**. It is tested separately so a
future `IR + sanitized Lean context` arm can use it deliberately. That would be
a different information policy: Lean hypothesis types can expose structure
that the arithmetic reifier discarded.

D1 has 17 genuine entries, including six let-bound facts. All six facts also
appear among its arithmetic rows. C8 has three genuine entries and no lets;
it cannot demonstrate proof-body redaction. The unit suite includes a synthetic
context containing both a declaration placeholder and an auxiliary proof body,
asserts those preconditions, accepts its sanitized projection, and rejects
unredacted and partially redacted variants.

The `_proof_` substring rule intentionally fails closed. An auxiliary constant
can occur in a legitimate original hypothesis type, so that rejection alone
does not establish a sanitizer leak. Fixture v1 currently uses the same error
for that case and actual forbidden material. The next policy must distinguish
source-context admission review from payload-integrity failures before task
expansion; neither condition may silently drop a fact or admit a payload.

The strict-IR choice is the implemented default for this fixture checkpoint.
The separate source-context preference remains a decision to confirm before a
live policy is frozen. No source-context or provider-specific prompt is implied
by this implementation.

## Frozen policy and evidence path

[fixture-farkas-v1.json](policies/fixture-farkas-v1.json) permits one fixture
request, no fallback routes, integer coefficients, at most 32 support entries,
and at most 128 characters per coefficient. The request has a 2-second execution
wall budget, 1 CPU second, 192 MiB memory, and 128 KiB output. Setup and teardown
times are recorded separately by the existing supervisor. All stages, including
preparation, have resource records; the request budget does not pretend to be
the cost of the full episode. Provider, revision, and sampling fields are null;
model calls, model tokens and model monetary cost are zero.

The stages are:

1. Compile the task's permitted capture instrumentation and reify the frozen
   local goal. Preparation then runs the known human `omega` closer to preserve
   the control's context artifact. This is evaluator preparation, outside the
   proposal phase. It supplies no witness or proof text to that phase.
2. Run the SDK's existing pipeline and pure Farkas row compilation in an
   isolated process. Independently recompute the rows in Python. Reject further
   Farkas compilation omissions; retain reifier omissions separately.
3. Hash and validate the request; receive one isolated fixture response. Decode
   and check its binding. There is no deterministic recovery call or fallback.
4. Assemble the response witness into the SDK certificate envelope. Record
   `witness_proposer = fixture_response` and
   `certificate_assembler = sdk_proposal_assembler_v1` independently.
5. Verify that certificate in a separate SDK process. A well-formed but wrong
   coefficient vector reaches this step and fails here.
6. Re-elaborate the frozen obligation. The bridge requires the newly reified IR
   to equal the packet's input IR, then uses its existing envelope/witness checks
   and Nat term-mode reconstruction. It consumes the Farkas witness and uses
   residual `omega`. No ATP derivation is replayed.
7. Export the proof and invoke the existing isolated Lean 4.32.2 validator for
   both frozen targets. Require their names, types, dependencies, axiom policy,
   and local-proof binding. The local proof must reference
   `ProofBroker.TermMode.farkasContradictN`.
8. Record the verdict, seal the retained artifacts, and audit the policy-specific
   receipt order and cross-artifact bindings.

`recovery_started` and `recovery_finished` explicitly name `fixture_farkas_v1`.
The old numerical tier stays 1. The new verdict omits the conflated legacy
`certificate_producer` field and separately records verification, consumption,
ATP derivation replay, residual closer, and final proof replay. A future model
proposer must have a new identity and policy; it cannot inherit fixture
attribution by relabeling a report.

The two valid fixtures intentionally rescale the old witnesses: D1 proposes
`4·hZ + 2·neg_goal`; C8 proposes `524288·hhi + 2·neg_goal`. This checks that a
valid new proposal is accepted without inheriting the deterministic controls'
exact coefficient or recovery-branch requirements. C8's original golden remains
the test of exact-support recovery. This fixture policy invokes neither bounded
enumeration nor exact-support search.

## Admission and P6

[admission-v1.json](policies/admission-v1.json) freezes the membership and
mechanical rule before requests. D1 and C8 are development controls, not a
benchmark sample. `P6_hyp_le` is a translation-loss diagnostic, not a registered
runnable task in this step.

The diagnostic criterion has three conjuncts: a recorded dropped proposition,
independently established truth of the original obligation, and an independently
checked satisfying assignment for all IR hypotheses plus the negated goal.
Unknown evidence stays unresolved; failure to establish this sufficient
criterion is not a certificate of adequate reification. No conjunct depends on
the deterministic solver or proposed witness succeeding.

For P6, the source's `hhi` gives `n ≤ 2^42 − 1`, and its explicit `hP` fixes the
modulus. Thus the maximum left side is `1152921504606584832`, below
`18446744069414584321`. The saved reification observation names `hhi` as dropped.
The assignment `_pb_atom_0 = 70368744161281` satisfies the weakened IR and its
negated goal. [admission.py](admission.py) re-derives these facts from source,
log, and final IR pinned to commit `e627efe`, requiring each source/log anchor
exactly once. Solver `sat` text and Lean process exit status are not used as
truth checks. Zero supplies a non-vacuous satisfying value for the original
arithmetic assumptions.

This establishes an inadequate IR for P6. It does not prove that the dropped
hypothesis is the sole abstraction change responsible, nor does it audit all
possible translation defects. The reifier log is still a trusted-host
observation. A larger benchmark needs evidence producers appropriate to its
tasks; this P6-specific arithmetic checker is not a general Lean truth checker.

## Implementation and trust accounting

The SDK library sources come unchanged from `e627efe`. A separate
`.cache/proposal-instrumented` overlay adds the small preparation/assembly
executable. Its Lean dispatch modification reads an externally supplied packet
instead of calling solver dispatch. This is an intentional dispatch change,
not observation-only instrumentation. The full patch and base/modified source
hashes are retained. The downstream checks and reconstruction functions retain
their existing bodies, apart from the already established observations.

The ordinary `.cache/instrumented` overlay and old golden episodes stay separate.
`episode.py` adds a policy-specific audit dispatch and an explicit exception for
retaining the fixture's C source when sealing. Historical policy audits retain
their original receipt sequence and recovery requirements.

The publication audit uses the frozen task and policy as reference data, checks
the complete fixture command including mount sources and namespace flags, and
requires the recorded harness sources to match the policy's
[frozen source hashes](policies/fixture-harness-v1.sha256.json). It compares saved
source bytes with that record, not with a subsequently edited working tree.
Launching fixture v1 still requires the frozen checkout; changes to that
implementation require a new policy revision. It does not execute the binaries or
authenticate the host. Hashes and receipts establish artifact consistency and
recorded provenance; they are neither compilation nor model-inference
attestations. A malicious evaluator able to rewrite the entire trusted artifact
and its reference rules remains outside this boundary.

A late audit failure leaves `failure.json` even if a kernel-success verdict and
seal were already written. The auditor rejects such a directory. An accepted
kernel report by itself is never the full episode-completion predicate.

The retained proof is a typed expression export, not generated Lean source.
Ephemeral compilation products and raw duplicate exports are omitted according
to the seal; the fixture C source is retained explicitly. A retained-only copy
must still pass audit. As with R6-000, C8's containing target is a
statement-identical `exact hlt` wrapper and checks local-proof binding; D1 tests
embedding in a larger real containing declaration.

## Reproduction and checkpoint

From the repository root, using the R6-000 pinned tools/dependencies:

```bash
python3 experiments/r6/test_proposals.py --run-dir experiments/r6/runs/proposal-my-checkpoint
python3 experiments/r6/episode.py audit --episode experiments/r6/runs/proposal-my-checkpoint/d1_valid
python3 experiments/r6/episode.py audit --episode experiments/r6/runs/proposal-my-checkpoint/c8_valid
```

Native execution requires the same delegated systemd user cgroups and Bubblewrap
support as R6-000. `--units-only` runs only payload/admission checks and never
marks the full checkpoint passed. Existing output directories and frozen
admission files are not overwritten.

The retained checkpoint is `runs/proposal-checkpoint-v2/`. The earlier
development runs remain on disk and are ignored by Git. The timeout-label fix
was a test correction; v2 additionally freezes the source record so later
harness development does not invalidate saved v1-policy receipts. New runs
produce new evidence, not the bytes omitted from development runs.

The [checkpoint index](runs/proposal-checkpoint-v2/checkpoint.json) records
**32 payload/admission checks, eight native fixtures, and 24 audit regressions**,
all passing. The native set contains two accepted controls and six rejected
corruptions across five failure categories. Both wrong-witness cases reject at
the same certificate-verification boundary. The audit set includes 16 coherently resealed mutations, two
retained-only positive copies, a check that current harness-source hashes are
not consulted, four historical golden audits, and preservation of 4,905 prior
committed artifacts. The old conformance suites were not re-executed in this
checkpoint.

```bash

```

The checkpoint directory, excluding `final-checks.json` itself, retains 764
files and 6,175,312 apparent bytes. Its 282 distinct contents total 4,045,699
bytes before Git compression or reuse of blobs already in the repository.
This is deliberate retention of positive episodes, native rejection traces,
and test reports. It is not a claim about incremental packed Git size.

The checkpoint runner keeps separate exact-name gates for unit checks, native
fixtures, and audit mutations. Each suite starts with `passed: false`, writes
each completed case immediately while still false, and checks for missing,
duplicate, or unexpected names before its final write. Wrong-witness controls
must first pass response decoding and then receive an arithmetic rejection from
a healthy verifier. Every native negative must retain its failure marker and
have no completion event, accepted verdict, or final seal.

`failure_stage` identifies the reporting detector, not a normalized logical
phase. Thus timeout reports native stage `proposal-1`; decoding, binding, and
request-budget rejection report logical phase `proposal`. Both wrong-witness
cases report `certificate-check` with category `certificate_verification`.
The [review closeout](reviews/2026-09-08/R6-001-REVIEW.md) maps the six cases
without changing their recorded labels. A later policy should add a separate
phase field while preserving detector-stage attribution.

Resealed audit mutations recompute both the event chain and seal so that
semantic checks, rather than stale hashes, reject false attribution, missing
request events, hidden fallback, changed inputs, and altered witnesses. Their
disposable full copies are reproducible from the retained positive episodes;
the mutation report records the changed artifacts and observed rejection.

The checkpoint is approved. Before connecting a provider, implement and freeze
the [live-policy requirements](LIVE-POLICY-REQUIREMENTS.md): explicit row semantics
in the actual model-visible prompt, its exact-byte hash in the request binding,
model revision, response envelope, retry/token/money limits, and transport failure
handling. Fixture success supports interface readiness only. It makes
no claim about model capability, search efficiency, benchmark breadth, or
complete protection against benchmark defects.
